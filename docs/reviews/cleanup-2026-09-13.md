# Gathering — repository cleanup and gameplay performance audit

**Reviewed 13 September 2026 · Minecraft 1.21.1 · NeoForge primary, Fabric secondary**

Repository: [MeekTheSneak/Gathering](https://github.com/MeekTheSneak/Gathering). Audited commit: `0e2502ed6c0418f0750560a57f56707268321a02`. The last successful remote HEAD check during the investigation matched this commit. A final repeat could not resolve github.com; changes published after the successful check are outside this audit. The new commit follows the previous reviewed `9fa4f73786b03b4191c0e529482eee1e1d7b3050` and changes 15 files, +684/−49 lines. **Recommendation:** proceed with a staged cleanup. The clearest gains come from doing expensive work fewer times: board broadcasts, collection search, and derived board geometry. No production fixes, refactors, commits, pushes, or texture edits were made. Builds and audit probes ran in a disposable archive. The original checkout remains unchanged. This is an implementation handoff, not a claim that the proposed optimizations are already implemented.

## Recent fixes: two good results, two incomplete edges

**Tutorial counter flow: verified in the exercised path.** Opening `CountersScreen` preserved the local demonstration, and the editor read its sample `+1/+1` counter correctly. Routing the tutorial through the appropriate client view and retaining it while a child screen is open addressed the reproduced failures. This does not exhaustively certify every unrelated screen replacement or disconnect path.

**Malformed reward reload: supported by source and passing GameTests.** `Rewards.reload` now refuses to publish the replacement when parsing has problems. The new malformed-edit and clean-deletion tests passed in the baseline suite. Preserve both “keep last good configuration on failure” and “delete removed rewards after a clean reload.”

**CL-01 · P2 · Tidy still overwrites a newer rotation.** The prior zone-change case now passes: a card moved to the graveyard stays there. However, the new client probe created a Tidy preview, changed a selected battlefield card to rotation 90, then applied the preview; rotation became 0. The preview validates only continued battlefield membership, so a newer position/rotation or attachment change can still be stale. Source: [TableScreen.java:4850](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/common/src/main/java/dev/gathering/client/TableScreen.java#L4850), especially application at line 4871 and membership collection at 4897.

Reproduce with two selected battlefield cards, open the arrangement preview, change one selected card's position/rotation through the session, then apply. Store and compare the source position, rotation, attachment, and session identity used by the preview. For protection against changes between client validation and server processing, use an expected revision or explicit preconditions in the server request. Reject/recompute a stale arrangement with visible feedback. Preserve the zone-removal fix. Test rotation, translation, attachment, ownership/control, session replacement, and a server-side interleaving. Only rotation and zone membership were runtime-tested here; the other cases are required coverage, not additional proven failures.

**CL-02 · P2 · Enlarged menus still exceed the viewport.** At text 200% and interaction size 75%, the actual client produced a menu width of 792 GUI pixels in a 427-pixel viewport, starting at x=4. The latest row-height change helps vertical overlap, but the number of columns and total width remain unconstrained. Some actions extend beyond the screen. Source: [ContextMenu.java:115](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/common/src/main/java/dev/gathering/client/ContextMenu.java#L115). See `Gathering-cleanup-menu-overflow.png`.

Constrain both dimensions using an accessible scrollable or paginated layout. Measure labels and shortcuts with the scale that will actually be drawn; `GuiText.width` and its fitted-render fallback also deserve consolidation. Do not solve an accessibility setting by silently shrinking all text back down. Verify every action is reachable at the supported extremes, after resizing, with long translations, and by keyboard. Add a bounds assertion plus an actual click on the last action.

These are prerequisites for refactoring their surrounding code, rather than reasons to discard the successful portions of the fixes.

“Code-bearing” means a line remaining after lexical comment removal; it includes imports, braces, declarations, and literal content. It is not a count of executable statements or a complexity score. Production also contains 25,593 comment-only and 8,353 blank lines. Removing those would change the headline number without improving runtime performance.

The largest production file is `TableScreen.java`: 6,430 physical lines, 3,797 code-bearing. `DevScene.java` is 9,876 physical lines. Both are difficult review surfaces, for different reasons.

A conservative exact-sequence scan found seven groups of repeated 12-code-line windows across production files, principally prompt/list UI helpers, small JSON helpers, and loader camera mixins. This scan misses semantic duplication and shorter copies; it is not proof of no duplication. It does show why promises of deleting tens of thousands of duplicated implementation lines would be premature. An unreferenced-type scan yielded framework entrypoints, registration, platform implementations, and tools rather than a trustworthy list of dead gameplay classes. Metadata/reflection registrations must be checked before deletion.

**Reasonable shrinkage targets:** release packaging, retired feature creation paths, repeated UI/registration boilerplate, and redundant work. Splitting a large class or moving tests changes organization, not total repository line count. Keep useful tests and explanations of security, ownership, and persistence invariants.

## Measurements: where less work is likely to matter

These are same-machine Java 21 microbenchmarks against the compiled core, seven trials with warmup, median time per operation, and thread allocation counters. They exclude Minecraft networking, authorization, metadata delivery, rendering, disk latency, and full-session logs. They are neither JMH results nor live-server TPS/FPS claims.

| Synthetic operation | Current model | Alternative or implication |
|---|---:|---|
| 128 changes, 400 cards, six filtered views encoded after each change | 43.60 ms; 95.18 MB allocated | Encode six final views once: 1.97 ms; 7.03 MB |
| Same burst with 1,600 cards | 166.27 ms; 359.93 MB allocated | Encode six final views once: 6.55 ms; 26.85 MB |
| Search 10,000 known collection entries | 7.01 ms; 20.68 MB allocated | Parse-once prototype: 2.41 ms; 10.04 MB |
| One immutable `withCard`, 1,600-card state | 0.0439 ms; 189,056 bytes allocated | Repeated full-map copying is measurable |
| Compute stack depths for 400 / 1,600 positions | 0.059 / 0.925 ms | Cache unchanged derived data before considering a more complex algorithm |
| Encode two unchanged spectator views, 1,600 cards | 0.397 ms; 874,216 bytes allocated | Reuse one public snapshot and avoid unchanged sends |

MB here is decimal. The burst fixture has four seats and two spectators, 80% battlefield/20% library cards, and 128 direct model updates. Both variants retain per-card immutable state changes; only view-generation frequency differs. It does not implement a production batch request or prove equivalent handling of intermediate events.

The collection comparison asserts identical output for one known-card fixture and the query `t:creature c:g mv<=4 o:draw`; parsing is outside the prototype's timed loop. This is evidence for a targeted optimization, not validation of every search mode. Raw spectator view payloads were 20,912 bytes at 400 cards and 80,432 at 1,600, before Minecraft compression/framing.

## Ordered cleanup and optimization work

### CL-03 · High value: batch safe bulk actions and reuse filtered board snapshots

Every accepted action passes through `TableActions` and broadcasts the table. `TableBroadcast.sendToTable` builds a separate filtered/encoded view per seated viewer and spectator. Source: [TableActions.java:54](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/common/src/main/java/dev/gathering/server/TableActions.java#L54), [TableBroadcast.java:75](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/common/src/main/java/dev/gathering/server/TableBroadcast.java#L75), and [TableBroadcast.java:148](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/common/src/main/java/dev/gathering/server/TableBroadcast.java#L148). Bulk UI actions call the action path repeatedly; the existing `BulkBroadcastGameTest` also demonstrates broadcast count increasing with the number of changes.

Implement one bounded bulk request for a clearly defined operation, initially selected-card tapping or arrangement. Retain server validation for each card, deterministic event order, refusal semantics, log entries, and undo behavior. Publish the final snapshot once per intended recipient when intermediate snapshots are unnecessary. A server-enforced size limit is required; a client selection limit is insufficient.

Separately, serialize the public spectator view once per session/view revision. Do not reuse a seated or historian view for public delivery. Keep permission context in every cache key and invalidate on visibility, seat, log, undo, and session changes. Share encoded output only where the complete audience-visible data is equivalent.

**Acceptance:** the same final state, event history, and refusals as the unbatched operation; bounded server work for oversized/malicious input; fewer view builds and sends for 128 selections; no hidden-card leaks when seats, reveal permissions, or viewers change. Preserve animation/event feedback deliberately. Do not indiscriminately coalesce every peek, reveal, or other disclosure transition merely because it occurred in one tick.

### CL-04 · High value: stop rebuilding unchanged ambient boards

`TableBlockEntity` sends ambient snapshots every 40 ticks, and `sendAmbient` scans the level's player list and rebuilds each spectator view. `sendPot` also scans nearby players during table broadcasts, including when an unchanged pot is empty. Source: [TableBlockEntity.java:619](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/common/src/main/java/dev/gathering/block/TableBlockEntity.java#L619) and [TableBroadcast.java:99](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/common/src/main/java/dev/gathering/server/TableBroadcast.java#L99).

Track the last revision sent to each relevant viewer, with bounded lifecycle cleanup. Reuse public encoded output. New arrivals, re-entering viewers, and reconnects must receive the current board even if it has not changed. Empty/closed state is meaningful and must clear an old board or pot. Consider spatial audience indexing only after measuring many active tables; dirty-state suppression is the simpler first gain.

**Acceptance:** idle tables stop repeating equivalent payloads, entering spectators immediately receive current public state, leaving/unloading clears tracking, and a populated-to-empty pot clears correctly. Profile 2, 4, and 16 tables with moving viewers. Preserve range/dimension checks.

### CL-05 · High value, relatively contained: compile collection queries once and reuse result pages

`CollectionSearch` parses the same text for each candidate row. `CollectionView.searchNow` builds all rows, filters and sorts the pool, and only then slices the requested page on the server thread. Source: [CollectionSearch.java:109](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/core/src/main/java/dev/gathering/core/collection/CollectionSearch.java#L109), [CollectionSearch.java:150](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/core/src/main/java/dev/gathering/core/collection/CollectionSearch.java#L150), [CollectionView.java:132](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/common/src/main/java/dev/gathering/server/CollectionView.java#L132).

Compile the text query once per search and precompute expensive sort keys. Then consider a bounded cache of ordered results keyed by collection revision, metadata revision, complete filter/sort query, and player/pocket context. Page changes should reuse that result while its inputs remain unchanged. The current UI waits for submission; this is not a claim that a full search runs on every keystroke.

**Acceptance:** identical ordering, counts, unknown-card behavior, colors/types/rarities, ascending/descending results, and malformed-query behavior. Invalidate after trades, imports, pack opening, metadata arrival, and pocket changes. Recheck live ownership and inventory before collection mutations regardless of cached search results. Measure 1,000/10,000 entries and repeated page changes. Land parse-once before adding a cache so its benefit and regressions are independently reviewable.

### CL-06 · Medium/high value: compute a reusable board presentation

`TableStacking.depths` scans preceding cards for every position, so it performs quadratic comparisons. `TableScreen.everythingOnTheTable` reconstructs placed cards, stack depths, and attachment data during rendering and several interactions. Miniature rendering calculates similar data before its card drawing budget takes effect. Sources: [TableStacking.java:56](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/core/src/main/java/dev/gathering/core/ui/TableStacking.java#L56), [TableScreen.java:2258](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/common/src/main/java/dev/gathering/client/TableScreen.java#L2258), [TableMiniatureRenderer.java:756](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/common/src/main/java/dev/gathering/client/TableMiniatureRenderer.java#L756).

Introduce a derived immutable board representation from the already filtered `GameView`: ordered cards, card-ID lookup, stack/attachment relationships, and stable geometry. Cache it across unchanged frames. Keep camera-dependent projections, animations, hover, and text metrics separate or invalidate them appropriately on zoom, resize, GUI scale, and camera motion. Reuse existing geometry classes instead of creating a competing geometry model.

**Acceptance:** same hit target, layering, ownership, attachment treatment, and visible counters for crowded boards; no private-state input to the client cache; correct resize/camera behavior; fewer allocations in an unchanged frame. Screen and miniature attachment grouping currently differ in detail, so do not assume their inputs are identical. If a spatial algorithm is still needed after caching, preserve the existing pairwise proximity/order semantics; grouping by approximate grid buckets can change stacking behavior.

### CL-07 · Medium value, higher correctness risk: reduce immutable state copying

`GameState.withCard` copies the card map and then constructs a state whose canonical constructor copies collections again. Other state changes can copy the entire card map even when changing seat information. Compound placement/update operations create successive snapshots. Sources: [GameState.java:45](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/core/src/main/java/dev/gathering/core/game/GameState.java#L45), [GameState.java:179](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/core/src/main/java/dev/gathering/core/game/GameState.java#L179).

Evaluate a mutation builder scoped to one logical event, freezing once, or an internal construction path that safely shares proven immutable collections. Public APIs must still defend against mutable caller-owned maps. Preserve the event-sourced model: ordinary submissions already fold incrementally; full replay on every ordinary move is not the current problem.

**Acceptance:** earlier states remain unchanged after later actions; restore/refold and undo produce equivalent state; attachments and zones remain consistent; allocation decreases on representative event mixes. Do this after broadcast/search improvements, because it has wider correctness consequences. Add a location index only if profiling justifies its maintenance cost.

### CL-08 · Clear packaging cleanup: remove development implementation from release artifacts

The measured NeoForge release JAR is 3,096,184 bytes and contains 75 GameTest class entries plus two DevScene class entries. Their compressed contents total approximately 430,782 bytes, about 13.9% of that JAR's size. Fabric's 2,811,952-byte JAR also contains DevScene, approximately 114,968 compressed bytes. This is a modest artifact-size opportunity, not evidence of equivalent RAM or FPS improvement.

Move NeoForge test implementation and DevScene into development/test source sets or development mods. Fabric's existing `testmod` arrangement is a useful local precedent. Preserve all testing. **Do not just exclude DevScene.class from the JAR:** production `ClientTicks` directly calls `DevScene.tick`, which would leave a missing runtime dependency. Replace that coupling with a development bootstrap hook and a harmless production path. Sources: [ClientTicks.java:38](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/common/src/main/java/dev/gathering/client/ClientTicks.java#L38), [build.gradle:84](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/fabric/build.gradle#L84), [build.gradle:61](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/neoforge/build.gradle#L61).

This relocates roughly 25,921 physical lines of NeoForge tests and shared DevScene out of release source sets; it does not delete them from the repository. Split the 9,876-line DevScene into bounded scenarios as part of maintaining the test harness.

**Acceptance:** inspect both final JARs, launch real release clients and dedicated servers without development classes, retain nonzero expected GameTest counts and dev-scene execution, and check loader metadata. Measure final ZIP contents rather than assuming compressed-size savings exactly equal the current entry totals.

### CL-10 · Highest maintainability value: separate TableScreen responsibilities around existing components

The 6,430-line screen combines modes, rendering, pointer interaction, selection, actions, context menus, tutorial transitions, and replay controls. The repository already has useful `TableSurface`, `BoardGeometry`, `SurfaceBoard`, `TableStacking`, `TableAttachments`, an action catalog, and `ClientTableActions`. Build on those seams.

Suggested new responsibilities, not existing filenames: a mode/context object for live/demo/replay; a derived board presentation; a selection/pointer interaction controller; and action bindings that connect action IDs to availability and invocation. Keep `TableScreen` as the Minecraft screen facade. Extract one responsibility per review, starting with the presentation work in CL-06. Avoid a framework of dozens of tiny forwarding classes.

Use the same action binding for menu, palette, and keyboard routes where they represent the same action. Keep labels/help aligned with actual availability, while retaining server authorization. A selected-card ID index also avoids repeated whole-board scans in bulk target lookup.

A useful feature improvement during this work is persistent inspection of a card chosen from an overlap list. The current chooser opens a card menu; selecting the inspection action must continue referring to that selected card, rather than resolving the top card under the pointer again. Source: [TableScreen.java:4823](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/common/src/main/java/dev/gathering/client/TableScreen.java#L4823). Treat this as a focused behavior change with its own validation, not an incidental outcome of moving code.

**Acceptance:** equivalent mouse, keyboard, palette, menu, replay, tutorial, and child-screen behavior; rebinding and accessibility checks; explicit mode transitions; private/demo/live state isolation. Success means fewer responsibilities to understand per edit, not an arbitrary per-file line limit.

### CL-12 · Profile-driven improvement: persistence and client preference writes

Replay loading/folding already uses a worker and replay headers already have a cache. However, closing a game synchronously encodes and writes its replay in `Replays.keep`, including retention cleanup. Block-entity saving also creates a serialized/encrypted session snapshot through `StoredSession.of`. Sources: [Replays.java:101](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/common/src/main/java/dev/gathering/server/Replays.java#L101), [TableBlockEntity.java:952](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/common/src/main/java/dev/gathering/block/TableBlockEntity.java#L952). Long-match disk hitches were not timed in this audit; this is a source-backed profiling target.

For replay finalization, capture an immutable snapshot and destination identity, use a bounded worker with atomic replacement, and report success only after persistence succeeds. Flush or safely drain work at shutdown. Cache unchanged serialized session data by a correct revision where appropriate; do not move vanilla block-entity saving to an arbitrary worker or return stale save data.

Client settings already debounce, but their eventual write is synchronous and directly replaces file contents. `RecentThings` already offers a stronger temporary-file/retry pattern. Consider one bounded latest-snapshot writer, preserving retries and shutdown behavior. Source: [ClientSettings.java:602](https://github.com/MeekTheSneak/Gathering/blob/0e2502ed6c0418f0750560a57f56707268321a02/common/src/main/java/dev/gathering/client/ClientSettings.java#L602).

**Acceptance:** measured long-session close/save latency, reload correctness, write-failure recovery, no false “recorded” message, no stale world/session destination after disconnect, and settings surviving interrupted writes. Preserve confidentiality of stored sessions and replays.

## Gameplay polish and modpack qualification after cleanup

The performance changes should serve the manual Magic tabletop: quicker selected-card actions, responsive collection navigation, stable inspection of crowded Commander boards, and readable controls. Keep the first-seat tutorial overlay and easy replay/skip access; do not reintroduce a separate required practice table. Show understandable pending/completion/refusal feedback for actual slow requests, wired to production request lifecycles.

Use an explicit qualification matrix: four-player Commander plus two spectators; ordinary 400-card and stress 1,600-card states; 100–128-card selections; counters, tokens, overlapping attachments, ownership changes, undo, reveal/peek, late joins, reconnects, and chunk reloads. Exercise 2/4/8-seat layouts, supported text/interaction sizes, and large collections. Track server action p50/p95/p99, allocation, view builds and bytes per gesture, and client frame times on unchanged and changing boards. Compare identical hardware/scenes; do not invent universal frame-rate targets.

Qualify exact available Minecraft 1.21.1 loader/mod versions when assembling the pack. In particular, audit the `TableReach`, `TablePointer`, and `TableCameraView` coordinate/camera boundaries against an actual moving-structure integration; a normal stationary-table test cannot establish that compatibility. Keep optional rewards and crafting integrations data-driven and configurable. Test a boss reward profile reload and representative crafting chain with the installed pack. Avoid adding an integration abstraction or hard dependency before an actual supported mod/API requires it.

The existing pure-core/common/loader separation, visibility filtering, incremental game folding, bounded art cache, worker-based card fetching, and extensive test coverage are useful assets. Retain them. No texture work is part of this plan.

## Execution order and developer handoff

1. Fix CL-01/02 and add the concrete failing probes as durable regressions. Land the canonical gate/current-status cleanup early.
2. Land query parsing once, then collection caching separately. Move development/test implementation out of release builds with release boot checks.
3. Add bounded bulk transport and spectator/ambient snapshot reuse in separate changes, with explicit privacy and ordering tests.
4. Extract/cache board presentation, then reduce TableScreen's remaining responsibilities. Share small helpers only after their behavior is understood.
5. Profile the resulting build before changing immutable state internals or persistence threading. Retire legacy creation carefully; consolidate loader registration only if the resulting API is simpler.

For each change, record the problem, preserved behavior, measured or structural result, and tests that exercise production callers. A passing helper test is not proof that a feature is connected. Keep refactors and behavior changes reviewable separately; avoid unrelated texture or balance changes.
